# STELLAR NEXUS 星图终端

> 一款科幻风格的桌面天文可视化终端，同时包含 **现实星图** 与 **架空星图生成** 两大核心模块。

> 可一键打包为 Windows 单文件 EXE，也可在 macOS / Linux 上直接运行。

#### 观测点设置（南北纬 / 东西经 / 城市检索）

左侧「观测位置」面板分三步，避免手工敲带符号小数出错：

| 步骤 | 说明 |
| --- | --- |
| ① 按城市检索 | 内置**离线 GeoNames 城市库（69338 个城市、233 个国家）**，支持中文名、英文名、拼音与国家名；单击结果即自动填入坐标与时区，双击直接应用 |
| ② 手动输入坐标 | 纬度/经度只填**数值**，正负号由「北纬 N / 南纬 S」与「东经 E / 西经 W」勾选框决定；下方实时显示「北纬 39.9042° 东经 116.4074°」与「北半球 东经」等提示，并额外提醒极圈/赤道/中高纬度的观测影响 |
| ③ 恢复默认 | 一键回到内置默认观测点（北京），应用后不影响其它设置 |

**默认观测点固定为北京（北纬 39.9042°、东经 116.4074°、UTC+8）**，启动时不再自动做网络定位，
所以每次打开看到的都是北京的天空。需要自动定位时点「IP 自动定位（会覆盖上面的坐标）」，
定位成功后会就近匹配库内城市名（例如把裸坐标显示成"北京"）。

### 核心功能 2：太阳邻域（50 光年内的全部已知天体）

以太阳为中心的三维视图，把**距离太阳 50 光年内、人类已编目的 860 个天体**全部画出来：

| 能力 | 说明 |
| --- | --- |
| 数据规模 | **860 个天体**（按恒星系统去重），全部距离 ≤ 50 光年，其中 808 个有 Gliese 编号、494 个有 HIP 编号 |
| 类型构成 | 主序星 730、白矮星 50、次巨星 20、巨星 8、类型待定 52（褐矮星/极暗天体仍在持续发现中） |
| 距离分布 | ≤10 ly：8 个｜10~20 ly：77｜20~30 ly：134｜30~40 ly：253｜40~50 ly：388 |
| 渲染方式 | 真实三维坐标（J2000 **赤道**直角坐标：X 指向 (0h, 0°)、Z 指向北天极），透视投影 + 深度雾化 |
| 参照物 | 太阳（原点，带光晕）、5/10/20/30/40/50 光年同心球壳、10 光年赤道面网格、比例尺 |
| 着色模式 | 按光谱型 / 按天体类型 / 按距离 / 按绝对亮度（四种一键切换） |
| 筛选 | 显示半径 5~50 光年滑块；按类型筛选（主序星 / 次巨星 / 巨星 / 白矮星 / 褐矮星） |
| 交互 | 左键拖拽旋转、右键平移、滚轮缩放、单击选中、双击聚焦；**右键菜单**可设为航线起点/终点、居中、连接最近星系、复制星系信息 |
| 信息卡片 | 编目编号（Gliese + HIP）、天体类型、光谱型、距离（光年/秒差距）、视星等、绝对星等、B-V、星座、银经银纬、赤道直角坐标、**最近的三颗邻居及距离**、备注 |
| 星图联动 | 卡片上的「在星图中定位」可切到现实星图并高亮该星 |
| 外星视角联动 | 在太阳邻域视图里选中某颗星后，从 `工具 → 🔭 外星视角` 打开对话框时会**自动以该星为观察点** |
| 数据来源 | HYG 星表 v3.8（Hipparcos + Yale 亮星表 + Gliese 近星表汇编） |

> 坐标框架说明：HYG 的 readme 把 `x`/`y`/`z` 写作"银道直角坐标"，但实测是**赤道**
> 直角坐标（把天狼的 x/y/z 代入 `atan2(y,x)` 得 101.2872°，正是星表自己的
> `ra = 6.7525h`）。早期版本按 readme 的说法当银道坐标处理，导致每颗近星的方向
> 都错了几十度。详见 [9.1 坐标框架勘误](#91-坐标框架勘误三个真实缺陷)。

> 实测抽查：比邻星（Gliese 551）4.227 光年、其最近邻居 Toliman 0.19 光年、巴纳德星
> （Gliese 699）5.948 光年、沃尔夫 359（Gliese 406）7.80 光年、天狼（Gliese 244A）
> 8.60 光年——均与天文年历一致。

### 核心功能 3：外星视角（从别的恒星看天空）

「工具 → 🔭 外星视角」（Ctrl+Shift+I）。把太阳邻域那份真实三维数据**反着用**：
站在 50 光年内的任意一颗恒星上，抬头看到的星空是什么样？

| 能力 | 说明 |
| --- | --- |
| 观察点选择 | 860 颗近星列表（按距太阳由近到远），支持搜索 `比邻星` / `Gliese 699` / `HIP 87937`；另有 5 个一键快捷按钮 |
| 三层数据 | ① 太阳（位置由坐标直接反算）② 50 光年内近星（**有真实视差**）③ 更远的亮星背景（按无穷远处理） |
| 太阳数据 | 视星等、所在星座、赤经赤纬、以及"那里的地球"视星等 |
| 视差对比 | 与地球视角逐星对比，给出角距：从比邻星看天狼差 26.8°、看南门二差 58.9°、看大角差 6.6° |
| 当地亮星表 | 该观察点夜空中最亮的 16 颗星（名称、视星等、所在星座、距离），双击即居中 |
| 全天球星图 | 球面透视投影、可拖动旋转 / 滚轮缩放 / 单击选中 / 双击居中 / 右键菜单 |
| 图层 | 50 光年内近星、远处亮星背景、银河带、黄道、赤经赤纬网格、星座连线、星名标注、红光夜间模式 |
| 星等上限 | 4 / 5 / 6 / 6.5 / 7.5 / 9 / 11 等七档，控制视野内恒星数量 |

**从比邻星看太阳**（实测输出）：视星等 **+0.39**，位于**天龙座**。
这是个值得记住的结论——以太阳的绝对星等 M_V = +4.83 算，4.2 光年外它只是
一颗普通的一等星，在当地的亮星榜上排不进前三。

科学口径（界面右侧逐条写明，避免误解）：

| 层 | 数据来源 | 精度 |
| --- | --- | --- |
| 太阳 | 坐标原点反算，`m = M − 5 + 5·lg(d_pc)` | 精确 |
| 50 光年内近星 | HYG 三维坐标 → 两星真实距离 → 视星等 | 位置含真实视差，精确 |
| 更远亮星 | 二维星表位置直接搬过来当背景 | 位移通常 < 0.1°，标为"无视差" |

星座判定用的是 88 星座中心点就近匹配，因此边界附近的天体会归到相邻星座——
界面上的相关文字都写成"位于 XX 方向"而不是断言"属于 XX 星座"。

> **性能（2026-09 修复）**：拖拽视角曾经卡到不可用，实测单帧 **2912 ms**
> （约 0.3 FPS）。拆开量每一步后定位到两处，都是"每帧重复做可以只做一次的事"：
>
> | 缺陷 | 根因 | 修法 | 实测 |
> | --- | --- | --- | --- |
> | 星座连线 2845 ms/帧 | 每个连线顶点都要在 8873 颗背景星里**线性扫**最近的星，约 1500 顶点 × 8873 = 1300 万次距离计算 | 按"顶点 → 当地坐标"建字典缓存（连线形状与视角无关，只需在换观察点时失效） | 2845 → **5.9 ms** |
> | 恒星绘制 31 ms/帧 | ① 每颗星每帧重算 `radec_to_vec`（含三角函数）② 每颗星一次 `drawEllipse`，PySide6 每次调用都跨 Python/C++ 边界 | ① 单位向量与颜色在建池时算好，每帧只做三次点积 ② 同色同半径合并成 `QPainterPath`，一次 `drawPath` 画完 | 31 → **18 ms** |
>
> 整帧 2912 ms → **35 ms**（约 28 FPS），拖拽已可用。

### 核心功能 7：观测计划表（今晚几点、什么高度、能拍多久）

「工具 → 观测计划表」（Ctrl+Shift+P），或现实星图左侧「生成今晚观测计划表」：

| 能力 | 说明 |
| --- | --- |

> 拖拽**确实**改了 `yaw`/`pitch`，问题在于**没有请求重绘**。
> `_emit_view()` 原来只 `emit` 信号，而重绘依赖 `_on_tick` 的静止判据——
> 它只认两种情况：① 时间在推进（`playing`）② **有飞船在航线上**。
> 而新生成的宇宙**飞船数是 0**（小型 40 / 中型 80 / 大型 140 / 超大型 220
> 四档实测都是 0，飞船要用户手动"派遣"才有），于是 tick 每帧直接 return、
> 一次都不重绘；一旦派一艘船，动画让每帧都重绘，同一个拖拽又"突然好了"。
> 修法：`_emit_view()` 末尾补 `mark_dirty()`——视角变了就必须自己请求重绘，
> 不能假设定时器会替你做。
>
> 排查教训：**用脚本模拟拖拽 + 强制 `render()` 是看不出这个 bug 的**——
> 强制渲染绕过了"有没有人请求重绘"这一层。`tools/check_fiction_drag.py`
> 因此断言的不是"像素变没变"，而是**"拖拽有没有把脏标记立起来"**；
> 它同时锁住"新宇宙飞船数为 0"这个触发条件，避免以后改生成器时把这条
> 复现路径弄丢。

#### 乐器层：钢琴 / 吉他 / 钟琴（v1.1.0 新增）

和声垫是"没有音头"的氛围音；想让星图真的**演奏**起来，需要带音头的乐器。
四个可选（默认仍是氛围垫）：

| 乐器 | 合成方式 | 实测"音头/尾音"能量比 |
| --- | --- | --- |
| 氛围垫 pad | 48 声部加法合成（原方案，无音头） | —（对照，无音头） |
| 电钢琴 epiano | 2 算子 FM，调制指数从 2.5 快速衰减（Rhodes 味道） | **13.5×** |
| 钢弦吉他 guitar | Karplus–Strong 拨弦：噪声激励 + 延迟线反馈 | 极大（2 秒后已衰减到 0） |
| 钟琴 bell | 非谐 FM（载波 + 2.76 倍频调制） | **9.6×** |

Karplus–Strong 那个延迟线的滤波系数**不能写成常数**：它决定"每经过一个周期
衰减多少"，而周期长度随音高变化——常数会让低音衰减过快、高音几乎不衰减。
正确做法是把它折算成"想要的余响时间"（`a = exp(-2/(RING·sr))`）。

##### 混音配平：这条比合成算法更容易出错

"加了钢琴却听不出来"整整查了一轮，根因全在**混音**上，三个都是实测出来的：

| 现象 | 实测数字 | 修法 |
| --- | --- | --- |
| 和声垫把乐器埋住 | 27 颗星全上时垫子峰值 **0.297**，而一次乐器音符只有 **0.051** —— 伴奏比旋律响 6 倍 | 垫子限 **9** 个声部（只留最亮的），峰值降到 0.18 |
| 低音线与铃声**常驻发声** | 乐谱清空后它们仍在响：RMS 恒为 **0.063**、包络一条平线（因为它们只依赖拍点与和声级数、与乐谱无关） | 两者都用 `has_harmony` 门控，没乐谱就淡出 |
| 伴奏没给乐器让位 | 只把垫子乘 0.62 时，乐器/伴奏的能量比仍不足以听出差别 | 有乐器时：垫 → 0.55、低音线与铃声 → 0.55、乐器电平 → 1.25 |

配平后的实测（30 秒，与纯垫子逐样本相减得到"乐器贡献"）：

| 乐器 | 混音 RMS | 乐器贡献 RMS | 占混音比 | 包络主频 |
| --- | --- | --- | --- | --- |
| 电钢琴 | 0.0452 | 0.0208 | **46%** | 0.434 Hz（= 半拍） |
| 钢弦吉他 | 0.0426 | 0.0154 | **36%** | 0.284 Hz |
| 钟琴 | 0.0477 | 0.0264 | **55%** | 0.434 Hz |

差异信号的谱峰落在 **330 / 262 / 586 Hz**（E4 / C4 / D5）——都在自然小调音阶内，
证明乐器确实在按和声演奏，而不是加了点噪声。
另外立体声也变宽了（左右相关 0.71 → 0.48~0.59），因为乐器声部按序号铺开了声像。

> 自检覆盖（`tools/check_sonify.py` B2 段）：
> 三种乐器的音头能量比 ≥3×、两两音色差异 >0.15、
> **乐谱为空时完全安静（RMS < 1e-4，修前 0.063）**、
> 30 秒里触发出的音头数 ≥4。
> `tools/make_sonify_sample.py` 会导出六个样例（三种音景 + 三种乐器），
> 其中钢琴/吉他/钟琴三轨是**同一片星空换乐器**，便于直接对比。

#### 排障：「完全没声」的三个根因（v1.1.2 修）

这三个都是**静默**故障——父进程看到"状态字=就绪、水位在涨"，
听起来却完全没声音。逐个记下来，因为每一个都值得单独防：

| # | 根因 | 为什么难发现 | 现在怎么防 |
| --- | --- | --- | --- |
| 1 | **magic 被参数覆盖**：`pack_into(buf, 8, SHM_MAGIC)` 的字节 8~15 正好是标量下标 1 = `SH_MASTER`。父进程每设一次音量就把魔数砸成 `float(0.55)` 的位模式（实测子进程读到 `0x3fe199999999999a`） | 子进程"就绪"了、水位也在涨，只是**所有音符都被判为无效**（notes=0）→ 合成静音。冲突是"看起来毫不相关的一行"造成的 | magic 移到**独立槽** `SH_MAGIC_WORD=6`；自检断言"所有标量槽取值两两不重复" |
| 2 | **`_HARM_SIGS` 元素类型错**：`SPECTRAL_VOICE.values()` 是 `(音区, 级数, 谐波)` 三元组，直接当谐波表用，`for amp in v.harmonics` 拿到整数/元组 → `TypeError` | 异常被 `render_tick` 的 `except` 吞掉，子进程**继续以 60Hz 写全零 PCM** | 解构出第三项；自检断言"每个元素都是纯 float 元组" |
| 3 | **`struct` 格式写错**：`unpack_from("<ff", …)` 只解 2 个浮点，紧接着取 `p[2]` → `IndexError` | 同上，被 except 吞掉 | 改成 `<fff`；并给 `render_tick` 加兜底：**连续 5 次渲染异常就主动退出**，让父进程的降级逻辑接手（宁可退回同进程合成，也不要稳定地放静音） |

**通用教训**：`render_tick` 里的异常**绝不能只记录然后继续**。
实测就是这条导致的"完全没声"——父进程的判据（状态字 + 水位）
**全部通过**，因为子进程确实在跑、确实在写。
所以 `tools/verify_exe_audio.py` 现在多了一条判据：
**采样 PCM 的「内容」**（峰值 > 0.01、8 次采样无全零），而不只是水位。

> ⚠️ 那条新判据自己也要用对：这一版给低音线与铃声加了 `has_harmony` 门控
> （没有乐谱就完全安静），所以**不给音符时全零是正确行为**——
> 探针必须真的往共享内存里写几条音符，否则会得到一个假失败。

#### 为什么合成要放在**子进程**里（这是"旋转星图时卡顿"的唯一有效修法）

用户报"旋转星图时音乐卡顿中断"。用真实鼠标事件拖拽 6 秒、同时量三件事，
拿到的是干净的因果链：

| 指标 | 同进程线程（旧） | 子进程（现在） |
| --- | --- | --- |
| 生产速率（产出音频秒 / 墙上秒） | **0.81×**（欠账） | **2.02×** |
| 环形缓冲最低水位 | 0，归零 **40.6%** 的采样点 | **743 ms**，归零 **0%** |
| 单块合成耗时（含等 GIL） | 22.8 ms（中位）/ 104 ms（最差） | 由子进程自主节拍，不受主线程影响 |

根因：主线程画一帧星图要 **70~114 ms**，这段时间 GIL 基本被它占着；
音频线程虽然每块只要约 1 ms，却常要等 40 ms 才轮到一次。
**同一进程里的任何线程方案都绕不开 GIL**，所以改成：
子进程自己合成、自己开 `QAudioSink`，父进程只负责
①每 100 ms 把 48 条音符参数写进共享内存（几微秒）②从共享环取 PCM 交给声卡。
子进程有**自己的 GIL 和自己的解释器**，父进程再卡也影响不到出声。

顺带修掉的三处（都在这一轮里量出来的）：

* **块长 512 → 2048 帧**（11.6 ms → 46.4 ms）：原来"合成一块 19 ms 而块长只有
  11.6 ms"，生产天生就欠账。加大块长把预算提高到 46 ms。
* **正弦查表 + 相位步进向量复用**：整块 `np.sin` 是每块最贵的一步，
  改成"算一次相位索引 → 查表"，每块耗时 19.1 ms → **2.7 ms**。
* **混响从标量循环改成向量化梳状递推**：原来那个 2048 次/块/声道的纯 Python
  循环**全程持有 GIL 不让出**，是"叠加渲染负载后飙到 49.8 ms/块"的主因。
  改成按块递推 + 卷积核，实测 **2.7 → 1.05 ms/块**。

#### 为什么不用"每颗星唱自己的频率"，而用七声自然小调

这是这个功能**能不能听**的关键，也是返工最多的地方：

| 做法 | 实测结果 |
| --- | --- |
| 每颗星用自己的频率（12 平均律） | 相邻亮星的频率毫无关系，同时响起来是一堆小二度与增四度 → **噪音** |
| 把光谱型映射到 A 小调五声音阶 | **任意组合都协和**，但只有 5 个音级——**一换和弦就跑调**（见下） |
| **7 声自然小调 + 按"音级"平移** | 同时满足"能换和弦"与"任意组合协和"（当前方案） |
| 直接"按星等取最亮 48 颗" | 天空中最多的就是 A/F 型同亮度恒星 → **48 条乐谱全部落在 329.6 Hz 一个音上**，听起来像持续警报音 |
| 按音高分桶限量（每桶 ≤3）+ 桶内 55 音分铺开 | 实测 18~27 条乐谱落在 14~16 个音高上，音区 110~1053 Hz |

**五声音阶为什么不够**（这条是"太单调"那轮才量出来的）：
要把"每 16 拍换一次和声"做出来，就得把整组音高平移。
五声音阶只有 5 个音级，按**半音**平移后音级会跑出原集合——
实测 `+3` 半音后变成 `[1,3,6,8,10]`，出现小二度与三全音，听感发脏。
换成 7 声自然小调之后，只要**按音级平移**（`k` 级 ≈ `k×12/7` 半音），
平移结果永远是这个音阶的子集。自检里两条断言把这个性质锁住了：
「所有光谱型只落在音阶的 7 个音级上」+「四种推进平移后都仍是子集」，
并留了"五声音阶 +3 半音会越界"作为反例对照。

#### 还有三个只有量了才会发现的坑

* **软限幅的驱动量必须小**。`tanh` 一旦进入饱和区就产生**互调失真**：
  驱动 0.9 时 FFT 里出现 915 Hz 这类既不属于任何一颗星、也不在音阶上的峰
  （它是 392+523 的和频），听感是"嗡"的脏。驱动降到 **0.30** 后谐波干净，
  响度不足的部分由 master 线性补偿（线性放大不产生新频率）。
* **淡出判据不能用 `v.target <= 0` 当"没有目标"的代理**。它记的是音级，
  一旦赋值就恒为正、下一块还要拿它做就近匹配，所以乐谱撤走时它永远不会变回 0
  → **声部永不淡出**，实测"乐谱清空后 3 秒仍以满音量持续发声"。
  正确做法是每块用一个 `claimed` 标志记录"这一块有没有被认领"。
* **"和声推进"必须写在合成器内部，不能写在子进程的定时循环里**。
  写在循环里的话，离线自检单独调 `render_block()` 时它永远不推进——
  实测"离线跑 40 秒，和声一动不动"，于是**"太单调"这个问题在自己的自检里
  完全看不出来**。移到 `render_block` 内部之后，自检才能断言
  「60 秒内换过 >=3 次调性中心」「铃音音高跟着变」「RMS 包络有律动」。
* **音阶级数必须是整数**。桶内铺开如果写成"级数 +0.34"，会被
  `pitch_hz` 里的 `int()` 吃掉——实测三个声部频率完全相同。
  改用**音分**（55 音分 ≈ 半个半音）表达，并把 `cents` 作为独立字段传下去。

> 试听：`python tools/make_sonify_sample.py` 会导出三轨 **36 秒** WAV
> （`sample_starry/galaxy/quiet.wav`），每 6 秒取一段做 FFT 就能看到主峰整组在换——
> 这就是"和声推进"的可听证据。**自动化断言只能保证"音高在音阶上、电平不削顶、
> 声部会淡出、和声真的在换"，"像不像轻音乐"只能靠耳朵**——所以专门留了这个脚本。

#### 子进程通信踩过的四个坑（每一个都让功能"看起来没坏但就是没声"）

做"子进程合成"时踩的坑，比合成算法本身的坑还多，而且症状全是**静默**的：

| 坑 | 症状 | 正确做法 |
| --- | --- | --- |
| `--windowed` 打包后 `sys.stdout`/`sys.stderr` 是 `None` | 子进程里所有 `print` 与报错**全被丢掉**，父进程永远等不到就绪信号 | 状态必须走共享内存（见下） |
| `subprocess.Popen` 默认 `close_fds=True` | 子进程**继承不到**额外管道 fd，拿到 -1 → 退回 stderr → 又踩上一条 | 别依赖 fd 继承 |
| 继承来的管道 fd 在冻结环境里读出来是 `EBADF` | 实测 `os.read(3)` 报 `Bad file descriptor`，孤儿防护静默失效 | 用共享内存心跳，不碰 fd |
| `QSocketNotifier` 在 Windows 上只对 **socket** 有效 | 对匿名管道根本不触发 → 父进程关掉后子进程一直活着变孤儿 | 在渲染节拍里轮询，或用心跳 |

最终方案：**父子只通过一块共享内存通信**
（标量参数 + 48 条音符 + PCM 环形缓冲 + 启动状态字 + 双向心跳），
不依赖任何 fd 继承、不依赖任何 stdout。

> 诊断这类问题的经验：**给子进程留一条诊断日志通路是值得的**。
> 一度因为把子进程 stderr 扔进 `DEVNULL`、又没有别的通路，
> 只能靠猜"它到底走到哪一步"，白花了一整轮。
> 现在 `_SNX_DEBUG_LOG=<文件>` 会让子进程把自己的状态追加进去。

#### EXE 里的音频子进程怎么自证（`tools/verify_exe_audio.py`）

源码模式下音频子进程是 `python -c <脚本>`；**打包后 `sys.executable` 是那个 EXE、
`核心` 包也在 EXE 内部不在文件系统上**，所以冰冻模式改成
"用同一个 EXE + 环境变量 `_SNX_AUDIO_CHILD=1`" 再起一次进程，由 `main.py`
顶部的入口接管。这条路**只有真的启动打包后的 EXE 才能验证**，判据是端到端的：

* 子进程把共享内存里的**状态字**置成就绪，并开始往 PCM 环里写数据
  （实测水位 1885 ms）——证明它认出了标志、在 EXE 内部 import 到了
  `核心.sonify`、并成功打开了 `QAudioSink`；
* 父进程"消失"后子进程自行退出（退出码 0），**不留孤儿**。

> 沙箱里跑这条验证要显式给一个可写的 `%TEMP%`：
> 单文件 EXE 启动时要先自解压，默认 temp 不可写时 PyInstaller 引导层直接报
> `Could not create temporary directory!` 并退出（退出码 4294967295），
> 看起来像"子进程不干活"，其实是环境限制。

#### 「拖拽时不中断」的常驻回归（`tools/check_sonify_under_load.py`）

"音乐在拖拽时不断"是用户直接报的缺陷，而它**不可能靠"跑起来没报错"发现**
——音频一直在响，只是缓冲被抽干时会有听不见的微小断点。所以固化成一个脚本，
每次改音频都跑一遍，判据是三条：

| 判据 | 实测 | 基线（同进程线程） |
| --- | --- | --- |
| 生产速率（子进程产出音频秒 ÷ 墙上秒） | **2.02×** | 0.81×（欠账） |
| 缓冲归零率（归零 = 声卡拿不到数据） | **0 / 63 = 0.0%** | 40.6% |
| 缓冲最低水位 | **697 ms** | 0 ms |

脚本自己会先确认"拖拽期间界面确实在重绘"（实测 6 秒内 64 帧、单帧 66.8 ms），
否则等于没施加负载、结论不成立。

> **量法本身也踩过坑**：不要去采样"另一个线程里的缓冲长度"——那需要额外的
> Python 线程抢 GIL，读数被 GIL 偏差污染（实测同一时刻能报出 *0 字节* 和
> *697 ms* 两种水位）。必须用**共享内存里的读写指针差**（父进程只读两个
> float64，无锁无争用），并叠一个**端到端**判据（子进程心跳增量 × 块长 ÷
> 墙上时间），两个数字互相印证。

| `pyinstaller>=6.3` | 打包时需要 | 生成单文件 EXE / .app |

> 只安装 `PySide6` 也能完整运行全部功能（含 DeepSeek 小说，因为网络请求使用标准库 urllib）。

### 3.4 性能说明

- 渲染由 `QTimer`（PreciseTimer，16 ms）驱动，两个视图都实现了**脏标记**机制：
  画面没有变化时完全不重绘，省下的 CPU 让相机操作与飞船动画始终顺滑
- 发光效果使用**预烘焙贴图缓存**（而不是每帧重建 `QRadialGradient`），
  在 CPU 光栅化下帧率提升约 3 倍
- 航线数量较多（>260 条）时自动切换细节层级：关闭抗锯齿与流动光点，保证交互流畅
- 银河带用**等照度轮廓 + 路径批处理**绘制（连续可投影段各自合并为一个
  `QPainterPath`），并做了两处关键优化：
  1. **暗带中心线按 1° 网格预计算一次**（暗带只随银经变化，与时间视角无关）。
     原先每帧现算 181 × 41 次遮挡查询，银河图层单帧 **134 ms → 79 ms**
  2. 只对"上下边界都能投影"的连续区间成路径。若把投影失败的点简单跳过，
     路径会跨过镜头背后的缺口连成巨大多边形——实测每行约 77 个亮像素，
     整幅画面被填亮（银道面是大圆，转一圈必然有一段在背后）
- 实测（离屏软件光栅化，1500×900，最苛刻场景）：
  - 现实星图：8883 颗恒星 + 149 条星座线 + 20 层银河带 + 网格
    ≈ **71~77 ms/帧**（1400×860，FOV 89.5°；离屏软件光栅化的重复测量抖动较大）
  - 架空星图（80 星系 / 169 航线）≈ **23 ms/帧**
  - 架空星图（220 星系 / 475 航线）≈ **60~90 ms/帧**
  - 在带 GPU 合成的真实桌面上（`update()` 走合成器路径）速度通常再快 2~4 倍
- 主线程不做任何耗时计算：位置计算按 0.25 秒节流，架空宇宙生成在 `QThread` 中执行

### 3.5 银河带是怎么画的（以及五次返工的实测数字）

银河带没有"标准答案"可比对，但**结构**可以客观测量。下面每个数字都来自
`tools/check_band_profile.py` / `tools/check_band_horizon.py` /
`tools/check_band_zoom.py` / `tools/check_milky_way.py`，不是肉眼结论。

画法：14→**20 层等照度轮廓**（每层是"上下边界都投影成功"的连续路径），
逐层用 `a = 1 − (1−105/255)^(1/20)` 叠加——多层半透明的合成是**乘性**的
（`T = Π(1−aᵢ)`），所以每层要贡献相同的净增量，而不是各自一个线性 alpha。
沿银经把 alpha 差值 ≤ 0.5 个亮度级的相邻列合并成一条 `QPainterPath`
（逐列画四边形要 146 ms/帧，合并后每层只剩几条路径）。大暗带（Great Rift）
用升余弦横向剖面挖空，横向再拆 4 层嵌套（见 `MILKY_RIFT_BANDS`）。

| 返工 | 症状（用户反馈） | 根因 | 实测数字 |
| --- | --- | --- | --- |
| ① 轮廓核写错 | 银河是几条平行竖条纹，"又脏又丑" | 每层用一个 alpha 套整层，包络成了**阶梯** | 相邻 0.1° 采样最大跳变 **17 个亮度级** |
| ② 暗带矩形核 | 银河边缘有一道**很直的斜边** | 横向 `\|x\| ≤ half` 一律填满 alpha、外面突变为 0 | 暗带边缘单步 17 级 |
| ③ 外层不收边 | 带缘有一条亮脊（"亮边"） | 20 层**同色**叠加，最外两层各贡献 6 级 | 带缘 15→23 硬台阶 |
| ④ 地下色偏 | 红模式下地平线下是一条**暗红**带 | 固定用深蓝去盖，与红模式夜空对不上 | 地下/地上 0.26 → 0.32（同一判据） |
| ⑤ 暗带太浅 + 单位算错 | 银河带中间那条缝隙"不够深" | `strengths[]` 已乘过 `RIFT_SCALE(0.45)`，填充 alpha 又乘一次，**0.45 算了两遍**，峰值 alpha 只有预期的 45% | 挖深 11.6 → **18.0 个亮度级** |
| ⑥ 暗带截断接缝 | 高倍放大时"银河带中间有一块缺失"，缺失区边缘是一条直线 | 暗带用"强度 < 0.12 不画"的**硬判据**，在 l≈96 一刀切断，而那个交界正好在银河最亮的一段里 | 相邻银经的半高宽变化 1.8°（判据 ≤ 4°，改前是突变） |

现在的参数与实测：

| 指标 | 数值 | 判据 |
| --- | --- | --- |
| 等照度层数 / 银经步长 | 20 层 / 2.0° | — |
| 外层渐隐 `MILKY_OUTER_TAPER` | 0.72 | 最外层乘 0.28，带缘是渐隐不是切断 |
| 暗带横向剖面 | 升余弦 + 4 层嵌套（`MILKY_RIFT_BANDS`） | 边缘被拆成 4 小级，不再是硬边 |
| 暗带淡入淡出 `MILKY_RIFT_FADE_LO/HI` | 0.02 / 0.20 | 强度低于 0.02 不画、高于 0.20 给满，中间线性——不再有截断接缝 |
| 暗带填充系数 `MILKY_RIFT_FILL_K` | 1.05（乘**原始**强度，不是乘已缩放值） | 挖深 18 级、核/侧翼 0.71 |
| 相邻 0.1° 采样最大跳变 | **5 个亮度级**（原 17） | ≤ 8 |
| 高倍放大（FOV 25~50°）带内台阶 | **4~7 个亮度级**、中心凹槽 ≤ 1 级 | ≤ 8 级、凹槽 ≤ 34 级 |
| 带缘单调性 | 无外缘亮脊 | 断言 |
| 带心 / 侧翼 | 0.81（关掉暗带时 1.17） | 0.70~1.00（用户反馈的那版是 0.34） |
| 带内 / 带外 ±20° | 55.7 / 22.7 | > 1.5 倍 |
| 地平线以下 / 以上（银道面过地平线处） | 18.0 / 57.0 = **0.32** | ≤ 0.40 |
| 全画面地下最大银河贡献 | 7（地上最大 191） | 地下 ≤ 地上 + 2 |
| 银河图层单帧 | ~90 ms（1400×860，20 层 + 4 层嵌套暗带） | 默认全图层 71~77 ms |

> 暗带的"单位算错"值得单独记一笔，因为它**看起来像调参问题、其实是单位问题**：
> `_draw_milky_rift` 里的 `strengths[]` 存的是"原始遮挡强度 × `MILKY_RIFT_SCALE`"，
> 而填充 alpha 的第一版写法是 `FILL_MAX × FILL_K × avg_s`——`avg_s` 已经缩放过，
> 于是 0.45 被乘了两遍。表现是"怎么调 FILL_K 都不够深"：把它从 1.35 提到 2.30
> 只让挖深从 11.6 涨到 14 级。改成 `raw_s = avg_s / MILKY_RIFT_SCALE` 之后，
> 1.05 就给出 18 级。**调参调不动的时候，先怀疑单位。**

> 地平线以下的压暗改过一次（第四版）：原先固定用深蓝 (2,6,12)/(1,3,7) 去盖，
> 红模式下盖在暗红夜空上就成了一条**暗红色**带，与上方暗蓝天空完全对不上
> （端到端冒烟测试截图里那条红带就是它）。现在基色与当前模式的夜空一致
> （正常 #040A14、红模式 #180604），只用**不透明度**随高度加深。
> 为什么不是"取上方像素颜色再乘系数"：夜空本身只有 15~20 亮度，乘系数会把
> 银河一起压没——实测那一版地下亮度只有 2，等于地下全黑；而固定基色 + 递增
> alpha 能"把银河压下去、把天空留下"。定标过程也记在代码注释里：alpha
> 110/140/180/215/238 @ y=0/8%/30%/60%/100%，实测地平线上方 57 → 地下 18（4° 处）。

> 三个测量陷阱记在这里，都是"判据错了比代码错了更常见"的实例：
> 1. 只开 `milky_way` 图层时，地平线以下的压暗**根本不会执行**——`_draw_underground`
>    挂在 `layers["horizon_grid"]` 分支里。第一版自检脚本因此把"没压暗"误报成
>    "银河在地下太亮"（同一像素 57 vs 开网格后 15）。
> 2. 图例色块用的就是银河带基色，亮度 204。未关图例时会把图例当成"地下最亮的银河"。
> 3. 画布正中的小十字准星、以及"银心方向 →"文字标记，都会给横剖面塞进一个
>    9~14 个亮度级的尖峰。`check_band_zoom.py` 现在**排除屏幕中心 ±14 像素**，
>    并且在量不了的档位（FOV > 50°、整条带不足 20 像素高）直接弃权而不是报失败。
>    同一条坑第三次出现：**判据必须先把 UI 元素排除掉，再去量画面。**
>
> 另：曾沿暗带加过 40 个**小尘埃斑**（`MILKY_DUST_PATCHES`）想让暗带不是一条
> 均匀的缝，经用户反馈后整条回退——所以现在暗带就是单一升余弦剖面，
> 不带任何斑块结构。

### 5.2 打包前的文档审计（第 4 步）

打包流程里插了一步 `tools/audit_readme.py`，核对本文档里所有"可验证的承诺"：

| 类别 | 核对内容 |
| --- | --- |
| A 数据计数 | 文档里的每个数字（星表 / 星座 / 深空 / 城市…）必须等于代码里的实际长度 |
| B 快捷键 | 快捷键表里的每组键必须在 `main_window` 里真的注册了 |
| C 菜单项 | 文档提到的「菜单 → 条目」必须真的存在于菜单树 |
| D 模块清单 | 实际存在的模块必须都写进第 8 章的结构图，且结构图不能列不存在的文件 |

**为什么要加这一步**：本项目已经三次出现「文档承诺了某行为、代码其实没接上」——
信息面板上的按钮不存在、选中近星后观察点传不进去、星表计数在三处互相矛盾
（769 / 770 / 781，且每处都与代码不符）。这类问题**不抛异常、不写日志、
界面照常打开**，只会让人下次排查时从错误的前提出发。

审计失败时的行为：

* `build.bat`：提示后询问是否继续（默认继续，不硬拦）
* `build.sh`：交互环境下询问；非交互环境自动继续
* 完全跳过：`set STELLAR_SKIP_AUDIT=1`（Windows）／`STELLAR_SKIP_AUDIT=1 ./build.sh`（macOS/Linux）

也可以单独跑：

```bash
python ../tools/audit_readme.py    # 在 stellar_nexus 目录外执行
```

### 5.7 PyInstaller 打包 PySide6 的常见问题与解决方案

| 现象 | 原因 | 解决方案 |
| --- | --- | --- |
| `could not find or load the Qt platform plugin "windows"` | Qt 平台插件未被打包，或混用了 conda / pip 两套 Qt | 确认只使用 `pip install PySide6`；重新打包时加入 `--collect-all PySide6` |
| 打包后界面没有样式（全灰） | `资产/styles.qss` 未被包含或路径解析失败 | 确认命令里有 `--add-data`；程序会同时查找「资产」与「assets」两个目录名 |
| `ModuleNotFoundError: No module named '核心'` | 中文包名未被自动收集 | 命令已包含 `--hidden-import 核心` 与 `--collect-submodules 核心`；也可在纯英文路径下打包 |
| 双击 EXE 一闪而过 | windowed 模式下看不到错误 | 把 `build.spec` 的 `SHOW_CONSOLE` 改为 `True`（或去掉 `--windowed`）后重新打包，用命令行运行查看报错 |
| 单文件启动慢（3~8 秒） | 每次运行都要解压到临时目录 | 改用目录版：`ONE_FILE = False` 后执行 `pyinstaller --noconfirm build.spec` |
| 杀毒软件误报 | PyInstaller 引导器的通病 | 加入白名单，或使用目录版、或对 EXE 做代码签名 |
| macOS 提示「无法验证开发者」 | Gatekeeper 限制 | `xattr -cr dist/StellarNexus.app`，或在「系统设置 → 隐私与安全性」里选择「仍要打开」 |
| Linux 报 `xcb` 插件错误 | 缺少系统库 | `sudo apt install libxcb-cursor0 libxcb-xinerama0 libxkbcommon-x11-0 libgl1 libegl1` |
| 打包体积偏大（60~120 MB） | PySide6 本体较大 | 已通过 `excludes` 排除未使用的 Qt 模块；如需进一步压缩可自行精简 `PySide6` 子模块 |
| UPX 压缩后无法启动 | UPX 对 Qt DLL 不友好 | 本项目 `build.spec` 中已强制 `upx=False`，请勿开启 |

### 9.1 坐标框架勘误：三个真实缺陷

这一节记录的是**数据层面的实质性错误**，不是标注问题。三个缺陷都是"算出来的数字
看着合理、只有拿真实天体对答案才会暴露"的类型，因此每一项都配了可复现的校验脚本。

| 缺陷 | 表现 | 定位手段 |
| --- | --- | --- |
| ① 秒差距当成光年 | 全部近星距离缩小 3.2616 倍 | 比 `\|(x,y,z)\|` 与 `distance_ly` |
| ② HYG 的 x/y/z 被当成银道坐标 | 每颗近星方向错 40°~150° | 用星表自带的 ra/dec 反推坐标系 |
| ③ 银道旋转矩阵转置存放 | 银经整体偏 113°（银纬却正确） | 与 PAL/SLALib 官方矩阵逐元素比对 |

#### 缺陷一：太阳邻域的坐标单位错了（秒差距当成光年）

`核心/nearby_data.py` 的 X/Y/Z 来自 HYG 星表的 `x`/`y`/`z` 列。HYG 的这两列
单位是**秒差距**，而项目把它当成光年直接入库，于是整个太阳邻域的三维坐标
整体缩小了 3.2616 倍。

| 检验项 | 缺陷值 | 正确值 | 比值 |
| --- | --- | --- | --- |
| 比邻星到太阳的距离 | 1.30 光年 | 4.227 光年 | 3.26 |
| 天狼到太阳的距离 | 2.64 光年 | 8.60 光年 | 3.26 |
| 巴纳德星到太阳的距离 | 1.82 光年 | 5.95 光年 | 3.26 |

影响范围：太阳邻域 3D 视图的比例尺、任意两星之间的真实距离、以及**外星视角**
里全部的视星等（视星等按 5·lg(d) 变化，距离错 3.26 倍就是 2.6 个星等的偏差）。

修复：生成脚本 `tools/make_nearby.py` 在读取时乘 `PC_TO_LY = 3.261563777`。
校验：`核心/nearby_stars.py` 里对全部 860 条记录比较 `|(x,y,z)|` 与 `distance_ly`，
最大偏差 0.15%、中位偏差 0.001%。

#### 缺陷二：HYG 的 x/y/z 不是银道坐标，而是赤道坐标

HYG 的 readme 把 `x`/`y`/`z` 写作 "Cartesian Galactic coordinates"，
但实测数据表明它们是**赤道直角坐标**（X 指向 (0h, 0°)、Z 指向北天极）：

```
HYG 里天狼：x = −0.494323, y = 2.476731, z = −0.758485, ra = 6.752481h, dec = −16.7161°
atan2(y, x) = 101.2872°      ← 与 ra = 6.752481h × 15 = 101.287215° 完全一致
asin(z / |r|) = −16.7161°    ← 与 dec 完全一致
```

项目原先把它当银道坐标，又转了一次赤道，等于对同一组数做了两次不同框架的变换。
后果是**每一颗近星的方向都错了 40°~150°**，星座判定完全乱套（从比邻星看天狼，
原先给出"天鹤座"，正确是"飞马座"方向差 26.8°）。

修复：`核心/inverse_sky.py` 的 `direction_from_offsets` 直接用 atan2/asin。
校验：`tools/check_inverse_sky.py` 断言"天狼必须回到 101.287°/−16.716°"。

#### 缺陷三：银道系旋转矩阵被转置存放（银经整体偏 113°）

`核心/astronomy.py` 构造银道系旋转矩阵时把矩阵转置存放，导致银经计算整体偏移
约 113°。这个缺陷特别隐蔽，因为：

* 银心方向仍然"对"（l=0 的定义点是矩阵本身取的方向，自洽）；
* **银纬完全正确**（转置只影响银经）；
* 银河带的形状看上去依然像银河带，只是经度分布错了。

实测暴露：

```
银北极 (192.859°, +27.128°) 的银经   缺陷值 235.913°   正确值 180.000°
天狼 (101.287°, −16.716°) 的银经     缺陷值 …          正确值 227.230°（天文年历值）
```

修复：`_galactic_basis()` 改为按**行**存放三根基轴（`v_eq = Rᵀ·v_gal`），
并在模块导入时执行 `_gal_check()` 自检——与 PAL/SLALib `eqgal.f` 的 IAU 1958
官方矩阵逐元素比对（最大偏差 1.6e-6），再用 6 颗亮星的银道坐标做端到端校验。
任何一项不通过，程序会在 import 阶段直接抛错，而不是把错误的银河带悄悄画出来。

#### 附带修正：标注与命名

* 「太阳邻域」3D 视图里的 `xy` 平面是**赤道面**而不是银道面，界面标签与文档已更正；
* 信息面板里近星的 "银道直角坐标" 一行改为 "赤道直角坐标（X→(0h,0°)，Z→北天极）"；
* 近星的 `galactic_l`/`galactic_b` 属性原先返回的其实是赤经赤纬，现已改为真实的银道坐标。

## 10. 性能与已知权衡

### 空闲 CPU：修复了一个会让程序"卡住不动"的严重缺陷

曾经的现象：程序启动后**什么都不做**，CPU 也长期占用 130%~196%（多核满载），
界面响应严重变慢，用户反馈"怎么不动"。根因是两处叠加：

1. **`FictionView._on_tick` 的自我永动循环**
   它先用 `update()` 清掉 `_needs_repaint`，紧接着又调用 `mark_dirty()`，
   而 `mark_dirty()` 会把 `_needs_repaint` 重新置为 `True` —— 于是下一轮 tick
   又重绘，形成「清标记 → 置标记 → 再清标记」的无限循环。
   实测架空星图在**没有飞船、也没推进时间**时空转 54 次/秒（单帧 21~28 ms）。
2. **`ScanlineOverlay` 扫描线覆盖层无条件动画**
   它是「透明 + `WA_NoSystemBackground`」的覆盖层，一旦重绘，Qt 必须把它
   底下的整个视图一起重绘。窗口里同时存在 4 个覆盖层（现实星图 / 太阳系仪 /
   太阳邻域 / 架空星图），各自 50 ms 动画一次，仅这一项就吃掉约 50% CPU ——
   等于为了 1 像素的扫描线漂移反复重绘整片星空。

**修复后实测**（offscreen，每 2 秒一个采样窗、连测 5 窗）：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 现实星图（无宇宙） | 196% | 0.0 ~ 3.9% |
| 现实星图（有宇宙数据） | 145% | 0.0 ~ 1.6% |
| 架空星图（可见） | 196% | 0.0% |
| 太阳邻域 | 173% | 0.0 ~ 13.3% |
| 太阳系仪 | 180% | 0.0 ~ 1.6% |

空闲时四个视图的重绘次数均为 **0**（脏标记机制真正生效）。

### 修复：星图整体上下颠倒（地平线跑到屏幕上方）

现象：默认视角（面朝正南、高度 +35°、视场 100°）下，**地平线出现在屏幕上方**，
"地平线下"区域占住上半屏——整个天球上下颠倒了。

根因在 `RealSkyView._camera()` 的相机基向量推导。本地 ENU 坐标（x=东、y=北、z=天顶）下：

```
屏幕"向右" = normalize(fwd × ẑ)        ẑ = (0, 0, 1)
           = normalize(fwd_y, −fwd_x, 0)
屏幕上向   = right × forward
```

原实现把 `right` 写成了 `-(fwd × ẑ)`（少了一个符号），朝南看时得到"东"而不是"西"，
于是 `up = right × fwd` 也跟着变成 `(0, −0.574, −0.819)`——指向**下后方**。
投影用的是 `sy = cy − focal·(v·up)/(v·fwd)`，`up` 反了就意味着高度角越大 y 越大，
天顶被画到屏幕底部、地平线被画到顶部。

校验（修复前 → 修复后，方位 180° / 高度 +35°）：

| 量 | 修复前 | 修复后 | 应有值 |
| --- | --- | --- | --- |
| `right` | `(+1, 0, 0)` 东 | `(−1, 0, 0)` 西 | 朝南时右手边为西 |
| `up` | `(0, −0.574, −0.819)` | `(0, +0.574, +0.819)` | 指向东北上方 |
| 天顶 y·up | −0.819（屏幕下方） | **+0.819（屏幕上方）** | 在上 |
| 南地平 y·up | +0.574（屏幕上方） | **−0.574（屏幕下方）** | 在下 |
| y 随高度角 | 递增（颠倒） | **递减（正确）** | 越高越靠上 |

修复后实测（同一视角）：

```
天顶 90°      y = −61.5   屏幕上方（相对中心 −371 px）
60°          y = 188.7   屏幕上方
40°          y = 287.2   屏幕上方
20°          y = 379.7   屏幕下方（+70 px）
南地平 0°     y = 492.1   屏幕下方（+182 px）
−20°（地平下）  y = 681.5   屏幕下方（+371 px）
左右：东（方位 90°）在左侧，西（方位 270°）在右侧 ✓
```

> 说明：这个问题同时影响所有依赖该相机的交互——右键"以此处为中心"的坐标反算、
> 悬停判定、双击居中在修复前都会算到错的位置。

### 已知权衡

- **架空星图的「时间推进」会持续占 CPU**（实测 150% 以上）：那是真实的飞船推进
  与多体计算，不是空转；暂停推进即回到 0%。机器较弱时建议用 20x / 100x 档位。
- **现实星图单帧约 85 ms**，拖动旋转时约 12 FPS：星图只在视角变化或时间推进时
  才重绘，静止时零开销；追求更高帧率可关闭「深空天体名称」与「地平线下天体」。
- 扫描线覆盖层现在**静止不流动**：这是刻意的取舍——动效的代价是每帧重绘整个
  视口，而观感差异几乎察觉不到。
- MP4 导出需要外部 `ffmpeg`（程序会自动探测 PATH 与程序同目录）；GIF 导出只需
  Pillow，已随打包内置。

### 想做但**没有**做的一件事：岁差时钟

设想是做一个「把星空搬到 ±5 万年」的时间机器：拖动年份滑块，看北天极在星空中
画圈、极星在右枢（公元前 3000 年）→ 勾陈一（现在）→ 织女一（约 +13700 年）
之间更替。恒星位置的部分我做出来了并且是可靠的（IAU 2006 岁差 + HYG 自行，
巴纳德星 1 万年位移 28.8°），但**天极方向**这一块最终没有交付，原因如下：

| 尝试 | 结果 |
| --- | --- |
| 用 IAU 2006 岁差矩阵把 J2000 黄极搬到目标历元，再构造天极 | J2000 锚点精确，但 +1 万年时推出的黄极赤纬与 `mean_obliquity` 自相矛盾，差 **4.7°** |
| 用该天极判极星 | 织女一的极星期被判成 **+15300 年**（天文年历值 +13700 年），右枢被判成公元前 1500 年（真实前 2700 年） |
| 改用闭合三角解 `t = 90° − ε − δ` | J2000 与 +2100 年正确，但 ±1.3 万年时天极赤纬偏离 +90° 达 **1.09°**——黄极自身的行星摄动漂移无法用短时段级数表达 |

结论：万年尺度的天极方向需要黄道面的长期摄动解（Simon et al. 1994 一类），
属于另一个量级的工程量。既然做不到，就**不放进程序**——而不是塞一个"看起来
像天文图"的近似进去，让用户以为 +5000 年的北极星是某颗真实的星。
恒星位置（`核心` 里那套岁差 + 自行）是独立且可靠的，将来若补齐摄动解，
这个功能可以直接接上。

## 12. 常见问题（FAQ）

**Q1：启动后显示「定位失败，已回退到北京坐标」？**
A：说明网络不可用或 IP 定位接口超时。手动在「观测位置」里填经纬度并点「应用」即可，不影响其他功能。

**Q2：为什么星星的位置和我手机星图 App 略有差异？**
A：本程序使用 J2000 星表 + IAU1976 岁差，未处理章动、自行与周年视差（对目视星图影响远小于 1′）。行星位置为几何视位置，与考虑光行差/章动的星历表可能有 0.01°~0.05° 的差别，肉眼与星图呈现完全一致。

**Q3：架空宇宙的随机种子会变吗？**
A：不会。随机数统一走 `random.Random(seed)`，同一个种子 + 同一规模 + 同一分布 = 完全相同的宇宙，可放心分享。

**Q4：时间推进时界面会不会卡？**
A：不会。位置计算按 0.25 秒节流，渲染仍按 60 FPS 进行；架空宇宙生成完全在 `QThread` 后台线程执行，主线程只负责绘制与交互。

**Q5：能同时打开多个窗口吗？**
A：可以运行多个实例，但本地存档槽位是共享的（保存在 `saves/` 目录）。

**Q6：程序报错怎么办？**
A：程序内置全局异常钩子，所有异常都会写入运行日志而不会让控制台崩溃。
菜单「工具 → 查看运行日志」可查看最近 120 条记录；日志中带 `TRACE` 的行包含完整调用栈。

**Q7：如何修改配色 / 界面风格？**
A：编辑 `资产/styles.qss`（控件样式）与 `ui/widgets.py` 顶部的颜色常量（自绘颜色），重启即可生效。

**Q8：为什么打包后的 EXE 有 60~120 MB？**
A：PySide6 本体包含 Qt 库。`build.spec` 已排除大量未使用的 Qt 模块，如需更小体积可使用目录版打包并手动裁剪 `PySide6/Qt6/bin` 下的无用 DLL。

**Q8-1：某些面板里的文字几乎看不见（浅底浅字）怎么办？**
A：这是 v1.0 的一个真实缺陷，已在 v1.1 修复。根因是 **QSS 只能作用于被选择器命中的控件**——
图层复选框的容器、信息面板的内层容器等普通 `QWidget` 没有被覆盖，于是退回 Windows 浅色
系统调色板（`#efefef`），浅色文字落在浅底上就"消失"了。
修复方式：启动时用 `app.setStyle("Fusion")` + `apply_dark_theme(app)` 把**整个应用调色板**
换成深色，再叠加 QSS，并给滚动视口与容器控件补上显式深色背景。
如果你从旧版本升级，请确认使用的是新的 `main.py`（其中包含 `apply_dark_theme` 调用）。

**Q9：行星看起来只是个光点，怎么看到「精细模型」？**
A：两种方式：① 在星图中滚轮放大到视场 < 30° 左右，行星与日月会自动切换成球体模型；
② 直接点击行星，右侧信息面板顶部会出现可拖动的 3D 模型（拖动自转、滚轮调相位）。
「工具 → 全天天体总览」的太阳系页也可以用「上一个 / 下一个」轮换查看全部 10 个天体。

**Q10：没有 DeepSeek API Key 能用历史小说功能吗？**
A：可以。未配置 Key 时点击「本地示例」，程序会用真实世界设定（势力、文明、星系、事件）
拼接出一段示例文本，用于预览排版与信息密度。配置 Key 后同一份设定会交给大模型改写成
真正连贯的小说。Key 支持两种提供方式：程序内设置（保存到 `deepseek_config.json`）
或环境变量 `DEEPSEEK_API_KEY`（优先级更高）。

**Q11：生成小说时报 401 / 402 / 429 怎么办？**
A：程序会把 HTTP 状态码翻译成中文提示：401 = Key 无效或过期，402 = 账户余额不足，
429 = 请求过于频繁（稍后重试）。也可在设置对话框里点「测试连接」快速定位问题。

**Q12：天体数量到底有多少？**
A：太阳系 11 个（太阳 + 月球 + 8 大行星 + 冥王星）／参与渲染的恒星 **8883 颗**
（主表 160 + 连线端点 621 + 背景暗星 8102；实际同时上屏约 900~3700 颗，
由光害极限星等决定，约 1250~5000 颗）／星座 88 个（连线 149 条）／深空天体 129 个／
太阳邻域 860 个（50 光年内）／城市库 69338 个。
「工具 → 全天天体总览」里可以逐条浏览与搜索。
这些数字与代码的一致性由 `tools/audit_readme.py` 自动核对。

**Q13：为什么地平线以下看不到任何天体？**
A：这是刻意的默认行为——只绘制"此刻真的能看见"的目标，画面更接近实际天空。
但如果你想查看**还没升起**或**刚刚落下**的目标，请勾选左侧「图层开关 → 地平线下天体」：
- 地平线以下的天体会以 **38% 亮度**绘制，名称前加 **↓** 标记，与真实可见目标区分
- 左下角图例会同步出现「地平线下天体（压暗 38%）」这一项
- 点击任意天体（无论在地上还是地下），信息面板的「升落」行会给出
  「约 X 小时后升起／落下（具体时刻）」，「最高高度」行给出未来 24 小时的最大高度角
- 对拱极天体（如北京看北极星）会直接标注「拱极天体（永不落下）」，
  对永不升起的目标（如北京看老人星）标注「永不升起（该纬度看不到）」

升落时刻的算法：以 4 分钟为步长在未来 48 小时内采样高度角，找到 0° 穿越点后
线性插值到分钟级精度，再按"当前在上/在下"判断下一次是落下还是升起。
实测：北京 2026-09-21 22:00，天狼（−44.3°）→「约 3.9 小时后升起（01:55）」，
织女一（+53.6°）→「约 5.6 小时后落下（03:37）」，北极星 → 拱极，
老人星 → 永不升起。

**Q14：为什么「最低风险 / 综合安全」规划出来的航线跳数更多、风险却更低？**
A：这是设计意图，也修正了早期版本的一个建模缺陷。原来的风险代价直接用
`risk × 100`，风险项完全压过距离，三种权重会给出**完全相同**的航线；同时对外
汇报的风险用严格累乘 `1 - Π(1 - ri)`，6 跳以上的航线会逼近 100%，等于宣告长途
航线"不可接单"。现在改为：

- 风险代价按 `risk²` 加权，让 0.2 与 0.8 的风险拉开 16 倍差距
- 规划的 `risk` 权重会主动绕行以避开高危区域 → 跳数增加但单跳风险更低
- 对外汇报的 `risk` 改用**单跳几何平均风险**并按跳数温和放大，严格累乘值单独
  保存在 `risk_cumulative` 字段里

实测同一对起终点（大型星区，16 跳 / 350 光年）：最短距离风险 0.521、
最省燃料 0.463、综合安全 **0.348**、最低风险 **0.262（24 跳）**——
五档权重终于有真实区分度。
